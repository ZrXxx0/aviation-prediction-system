# 修复迁移依赖问题

## 问题说明
数据库中已经应用了 `admin.0001_initial` 迁移，但它依赖于 `accounts.0001_initial`，而该迁移还没有被应用。

## 解决方案

### 方案1：使用 --fake 标记迁移（推荐）

如果数据库中**还没有** `user` 和 `role` 表，执行：

```bash
# 1. 先fake标记accounts的初始迁移为已应用
python manage.py migrate accounts 0001 --fake

# 2. 然后正常执行迁移
python manage.py migrate
```

如果数据库中**已经有** `user` 和 `role` 表（可能是手动创建的），执行：

```bash
# 1. 直接fake标记为已应用
python manage.py migrate accounts 0001 --fake

# 2. 然后正常执行迁移
python manage.py migrate
```

### 方案2：重置迁移历史（如果数据库可以重置）

如果这是开发环境，可以重置迁移：

```bash
# 1. 删除accounts应用的迁移记录（保留迁移文件）
# 在数据库中执行：
# DELETE FROM django_migrations WHERE app = 'accounts';

# 2. 然后正常迁移
python manage.py migrate accounts --fake-initial
python manage.py migrate
```

### 方案3：手动修复迁移依赖

如果以上方法都不行，可以修改迁移文件，移除对auth的依赖：

编辑 `accounts/migrations/0001_initial.py`，将 dependencies 改为：

```python
dependencies = [
    # 移除对auth的依赖，因为admin已经应用了
]
```

然后执行：
```bash
python manage.py migrate accounts --fake-initial
python manage.py migrate
```

## 推荐步骤

1. 首先尝试方案1：
   ```bash
   python manage.py migrate accounts 0001 --fake
   python manage.py migrate
   ```

2. 如果还有问题，检查数据库中是否有user和role表：
   ```sql
   SHOW TABLES LIKE 'user';
   SHOW TABLES LIKE 'role';
   ```

3. 如果表已存在，确保表结构与模型匹配，然后使用 `--fake` 标记

4. 如果表不存在，正常执行迁移即可
